# Loom

Loom runs a software project with agents. A planner agent turns a goal into a spec: the goal, the tickets with acceptance criteria, the checks that must pass, the review policy and the merge strategy. The human approves the spec and starts the project. The plugin, not an agent, owns every state change: agents get narrow tools for their role, and only plugin code moves a ticket, runs checks, merges, or decides that work is done.

Once a project runs, the plugin starts worker agents by itself, one per ready ticket, each in its own git worktree. Work that passes the plugin's checks is reviewed by separate reviewer agents, reworked until they approve, and then merged: into an integration branch, or as one pull request per ticket. For the integration strategy the human lands the branch upstream with one command. A project can also span several repositories: each ticket then changes one of them (see Multi-repo projects).

## Commands

    bb loom list                                  # projects with state and ticket count
    bb loom show <slug>                           # state, goal, merge setup, spec versions, ticket counts, next step
    bb loom spec <slug> [--version N]             # the spec as TOML (approved version, or the draft)
    bb loom tickets <slug> [--state s,s]          # the board: key, state, priority, title, dependencies
    bb loom ticket <KEY>                          # a ticket and its reply thread, indented by reply depth
    bb loom metrics <slug> [--days N]             # flow and agent metrics, one line each, with units; --days sets the window (default 14)
    bb loom feed <slug> [--after <id>]            # the newest 200 events as sentences, oldest first; --after gives the 200 after that id
    bb loom report <slug> [--send]                # the project's record as Markdown; --send runs the done hook again (human only)
    bb loom post <KEY> <text> [--reply-to <id>]   # the human's reply on a ticket; a worker that holds it gets it as a message, or the planner when it is blocked (human only)
    bb loom block <KEY> <reason>                  # block a ticket; its worker is stopped (human only)
    bb loom requeue <KEY> [--note <text>]         # send a blocked ticket back to the queue (human only)
    bb loom requeue <KEY> [--note <text>] --review  # review again as is: back to review, or back on its open pull request, with no new worker (human only)
    bb loom cancel <KEY> <reason>                 # cancel a ticket; its worker is stopped (human only)
    bb loom approve <slug> [--version N] [--skip-review]  # approve a draft and create its tickets, or apply a pending version; a draft waits for its spec review unless --skip-review (human only)
    bb loom start <slug>                          # ready to running; creates the integration branch (human only)
    bb loom pause <slug> [--now]                  # running to paused; --now also stops every worker thread (human only)
    bb loom resume <slug>                         # paused to running; stopped workers get a continue message (human only)
    bb loom archive <slug>                        # stop the workers, cancel open tickets, remove the sidebar section (human only)
    bb loom land <slug> [--title t] [--ready]     # push the integration branch and open one pull request to the base branch (human only)
    bb loom land <slug> --direct                  # merge in the remote's base branch, run after_merge, push to the base branch with no pull request (human only)
    bb loom land <slug> --repo <name>             # on a multi-repo project, land only that repo; goes with or without --direct (human only)
    bb loom sync <slug> [--ticket <KEY>]          # on the pull request strategy, read the open pull requests now instead of at their next check (human only)
    bb loom forge check <slug> <KEY or url> [--repo <name>] [--version N]  # read a live pull request through the repo's forge, as a poll would, and print what Loom reads; changes nothing
    bb loom rollout <slug>                        # the deploy order as sentences: the next safe step, warnings, each stage's steps, milestones and windows
    bb loom live <slug> <KEY|milestone> [--note t] [--undo]  # mark a rollout step or milestone live, or take the mark back; moves no ticket (human only)

Every command accepts `--json`. Failures carry a code: `loom_not_found`, `loom_invalid_state` (the message names the current state), `loom_invalid_spec`, `loom_invalid_input`, `loom_no_checkout` (the bb project, or one of the project's repos, has no checkout on the project's machine; the message gives the clone command), `loom_unavailable` (git or the repo's forge, `gh` or the spec's forge commands, is missing or failed on the project's machine; the message is the host's) and `loom_human_only`.

## Project states

- `draft`: proposed, not approved. The planner can revise it; each revision is a new version, older drafts read as superseded, and approving takes the newest. Approving waits for the newest version's spec review (see Spec review).
- `ready`: approved; its tickets exist. A revision now waits as a pending version until the human approves it.
- `running`, `paused`: started, and paused again. Moves: ready to running (start), running to paused (pause), paused to running (resume). Starting or resuming makes the project's sidebar section again if it was deleted, and moves the planner thread back into it. Pausing stops new work; workers already running keep going unless the human used `--now`. A check result that finishes while the project is paused is kept on the ticket, and a failed one reaches the worker when the project resumes. The plugin also pauses a running project when its token budget is used up or its deadline has passed, and says why in `bb loom show`.
- `done`: every ticket is done or cancelled. On the pull request strategy the plugin moves the project to done by itself; on the integration strategy `bb loom land` does. The plugin then deletes the project's sidebar section, and its threads go back to the ungrouped list.
- `archived`: reachable from any state; archiving stops the workers, cancels open tickets and removes the sidebar section.

## Ticket states

`queued`, `working`, `checking`, `review`, `approved`, `merging`, `pr_open`, `done`, `blocked`, `cancelled`.

- `queued`: waiting for a worker. A ticket is ready when every ticket it depends on is done and its scope does not overlap the scope of any ticket in working, checking, review, approved, merging or pr_open. On the pull request strategy with stacking (below), a dependency also counts once its pull request is open, and a ticket's scope may overlap the tickets it depends on, directly or through others, and the tickets that depend on it. At most `agents.max_workers` workers run at once: a worker holds a slot while its ticket is in working or checking, or while it writes the pull request of an approved ticket, unless it waits for the human's answer to a question. Work that goes back to a worker (a pull request's fix round, a review's requested changes, a merge that did not land) moves the ticket to working and waits there for a free slot, before any new ticket starts; the worker gets the message once it has one.
- `working`: a worker holds it. `checking`: the plugin is committing and running the checks. `review`: the checks passed; reviewers judge it. `approved`: enough reviewers approved it; it waits in the merge queue, on the pull request strategy also for the worker's `loom_pr`, and on a stacked ticket while two or more of its dependencies are open. `merging`: the plugin is merging it, pushing it to its pull request, or bringing a stacked branch up to date. `pr_open`: its pull request is open and the plugin follows it; a fix round takes it back to `working`, and a dependency that changed or merged, a base it fell too far behind or conflicts with on a repo that sets `refresh_behind`, or a new pull request in place of a stacked one the forge closed takes it to `merging`.
- `blocked`: it needs the human or the planner. It leaves blocked only by a requeue.
- `cancelled`, `done`: final.

## The ticket thread

Each ticket is the root of a reply thread. Its first post is the brief: the body and the numbered acceptance criteria. Claims, notes, submits, check results, reviews, block reasons and the human's replies become posts under it. Read the whole thread with `bb loom ticket <KEY>` before you work on a ticket: the human's replies and the planner's answers are instructions.

## Roles

- Planner: the thread that proposed the project. Before approval it revises the spec with `loom_propose`, after `loom_discover` has told it how each repo is reached (its remotes, whether `gh` serves them, the environment providers bb offers and whether Loom can add its own integration worktree). After approval it uses the board tools below, mostly to answer triage rounds. When the human has to act, it records the steps with `loom_ask_human` (below). It never approves, starts or pauses.
- Worker: a thread the plugin starts for one ticket. It has `loom_note`, `loom_submit`, `loom_block`, `loom_pr` and `loom_pr_reply`, and on a machine of its own `loom_resume` too.
- Reviewer: a thread the plugin starts to review a ticket. It has `loom_note`, `loom_checkout`, `loom_approve` and `loom_request_changes`, and changes nothing.
- Spec reviewer: a thread the plugin starts for each draft version and each pending version. It has `loom_spec_approve` and `loom_spec_request_changes`, and changes nothing.
- Any other thread has `loom_discover` and `loom_propose` and can start a new project.

A thread's role is whatever the plugin's own table says. Claiming a role in thread metadata grants nothing.

## Spec review

Before the human is asked to approve a version, a fresh reviewer agent checks it. When `loom_propose` saves a draft version, or a pending version of an approved project, the plugin starts a spec reviewer on the provider and model of `agents.reviewer`, in a worktree of the project's first repo at its remote base branch. A newer version stops the review of an older one. A pending version is reviewed as a change to the version in force: its brief lists what it changes, and its rounds count from 1 again.

The brief points the reviewer to the planning conversation (`bb thread log <planner> --format minimal --all`), whose human messages outrank the spec's goal; answers to the planner's Ask User Question rounds may be missing there, and the goal and non-goals record them. It also holds the spec, the findings of earlier rounds, and a rubric: every ticket serves the request, the fewest tickets deliver it, nothing speculative (configuration, flags, layers, generality the goal does not use), reuse what the repository has, nothing missing, each `project.done_when` item traced to the tickets whose acceptance criteria make it true, no ticket whose criteria can be met by documenting why the goal cannot be met (such as a change of comments alone), and real checks and narrow scopes.

- `loom_spec_approve({ summary })`: the spec builds what the human asked for, and no more.
- `loom_spec_request_changes({ summary, findings })`: `findings` has 1 to 20 entries, each `{ path?, title, detail }`, where `path` names the part of the spec, such as `ticket[csv-export].acceptance[1]`.

The verdict reaches the planner as a message. Every finding blocks the handover; the planner revises and proposes again, and a fresh reviewer checks the new version. After three rounds with findings the plugin stops reviewing that version, and the planner hands over with the findings it left open. A reviewer that ends its turn without a verdict gets one nudge; a second idle, an archived thread or a spawn bb refuses ends the review as failed, and the planner restarts it by proposing the same spec again. A rate-limited turn is retried when the window resets.

A version whose changes against the version before it touch only operational settings skips the spec review; the human still approves it. The version before a draft is the draft before it, whose own review must have passed or been skipped, and the version before a pending version is the version in force; the first version is always reviewed. Operational settings say how Loom runs the project, not what it builds: the forge (`merge.forge`, a repo's `forge`), environments (`environment`, a repo's or a ticket's `environment`), `agents`, `budget`, every `merge` setting but `strategy`, `branch` and `remote`, `checks.timeout_minutes`, `checks.ci` and a repo's `ci`. Anything else keeps the review: any other ticket field, project fields, scope, `checks.commands`, `after_merge`, a repo's checks or protected paths, the review policy, and adding or removing a repo or changing its project, base or remote. Loom records the review as skipped with the paths that changed, writes it to the feed, and sends the planner the hand-over a passed review sends, saying why there was no review; the Spec tab and the next-step bar say so too.

`bb loom approve` refuses a draft or a pending version whose review is running, has findings or did not finish; `--skip-review` approves it anyway and the feed records it. A skipped review does not hold approval back. The Loom page hides Approve while the review blocks, and the next-step bar says what the review is doing. A version's review stays on its Spec page after approval.

## Workers

The plugin starts a worker for each ready ticket: a new thread in the project's sidebar section, in its own git worktree, on the provider and model the spec names for workers. A fresh ticket starts from the integration branch (or from the remote base when the project opens pull requests); a requeued ticket starts from the branch the earlier worker left. The worker's first message is the brief: the ticket, the acceptance criteria, the scope and protected paths, the checks the plugin will run, the rules and, for a requeued ticket, the whole ticket thread.

A worker has these tools and no others:

- `loom_note({ text, reply_to? })`: record a milestone on the ticket. Use it once per milestone.
- `loom_submit({ summary, pr? })`: hand the work in when every acceptance criterion holds, then end the turn. The call returns at once. The plugin commits the worktree (the worker never commits), lists the changed files, runs the ticket's verify commands and then the project's check commands, and stops at the first failure. On the pull request strategy (unless `merge.describe = "loom"`), `pr = { title?, body? }` is the pull request as it should read. The plugin keeps it on the ticket as the proposed text, with the commit its checks passed with; a later `pr` replaces only the fields it gives, whole. The reviewers judge it with the work and may request changes to it. Loom adds its own sections after the description (the pull requests it depends on, the Rollout section, who opened it), so the worker writes neither those nor the deploy order.
- `loom_block({ reason, needs })`: say what is wrong and exactly what is needed, then end the turn. The work is saved on the ticket's branch and the ticket moves to blocked.
- On the pull request strategy, the plugin's checks are the cheap ones that run where the worker is, and every other test runs in the pull request's CI, unless the repo sets `ci = false`, which makes the plugin's checks the whole bar. The brief says which. A worker does not block, fail or loop on a test its environment cannot run, and names the tests it did not run in its `loom_submit` summary; a reviewer does not request changes only because a test was not run where it is.
- `loom_resume()`: only for a worker on a machine of its own (the repo's environment sets `machine`, or did when the worker started), whose brief starts with it as the first step. It carries in the work earlier workers left on the ticket, from the branch `loom/<slug>/<key>-home` on the project's machine (or, after a worker on the project's machine, from that worker's branch), as one commit on the base; for a stacked ticket it first puts in the commit the ticket is stacked on as a commit of its own, which the worker must keep. `loom_submit` is refused until it has. It refuses a worktree with uncommitted changes or commits of its own, which it would drop: stash them or move them to another branch, then call it again. On a failure it returns the reason: call it again, or `loom_block`.
- On the pull request strategy, a ticket with a rollout, or any ticket of a project with rollout stages, has a Rollout section in its brief: its stage, what must be live first, how it deploys, its release, whether it ships dark, verify and rollback. Loom writes the rollout order in the pull request's Rollout section; do not write deploy order or prerequisites into the description.
- `loom_pr({ title?, body?, commit_message })`: only on the pull request strategy, and only after the plugin asks for it once the reviewers approve. Write the commit's message, and the pull request's title and description unless you proposed them with `loom_submit`, the way you normally do, following your own instructions and skills for them, then end the turn. A title or body given here wins over the proposed one. In a fix round the plugin asks for the `commit_message`, and a title or body given then is set on the pull request after the push. Change no files: the plugin pushes the commit the reviewers approved. A worker that ends its turn without it gets one nudge; after the second idle, or 30 minutes, the plugin uses its own template for what was not proposed.
- `loom_pr_reply({ item, text, resolve? })`: only in a fix round on the ticket's open pull request. It answers one review, review thread or comment of the feedback Loom sent, named by the key the fix round's message gives it; an unknown key is refused. The plugin posts the reply through the forge on the project's machine, so it works on every machine: with `gh`, a reply in the review thread, then its resolution when `resolve` is true, or for a review or a comment a pull request comment that quotes its first line and links it; on a command forge, the spec's `reply` command. It ends the text with Loom's `commentSignature` setting ("Posted by Loom" by default; empty for none) and a hidden mark, posts the reply on the ticket, and answers with what happened or the forge's error. At most 30 per fix round. Answer review comments with it, never with the forge's CLI. A forge with no way to reply refuses it; say the answer in the `loom_submit` summary then.

What the plugin checks on a submit:

- A change to a protected path always fails the submit. A change outside the ticket's scope is flagged in the check post (`scope.enforce = "warn"`) or fails the submit (`"reject"`).
- The check commands must pass, and they must not write tracked files. The worker must not edit files while they run; if the worktree changed, the run fails.
- The result is a `check` post on the ticket. On a pass the ticket moves to review. On a failure the failing command's output goes back to the same worker, who fixes it and submits again. After `budget.max_check_failures` failed runs the ticket is blocked. On the Loom page, the ticket's check cards keep every command's output, exit code and duration, and its merge rows every git step.
- If the machine disconnects or a call times out, the worker is told to submit again, and no failure is counted.
- A worker on a machine of its own (see "Threads on new machines" in `references/spec.md`) runs the checks there. On a pass the plugin carries its commit back to the project's checkout, checked by tree, and that commit is what reviewers and the pull request get; a work-in-progress save is carried back the same way when its thread ends. A stacked ticket's commit is rebuilt on the commit it is stacked on. A submit is refused while its branch no longer has the commit `loom_resume` put first, or while a file Loom carried in with conflict markers still has one.

Limits that keep a ticket moving:

- A worker that ends its turn without submitting or blocking gets one nudge. On the second such idle its work is saved as a WIP commit, its thread is archived and the ticket goes back to the queue. The same applies when its turns keep failing.
- A ticket is blocked after `budget.max_attempts` failed attempts. A start that failed waits and tries again (after 1 minute, doubling to every 15 minutes) with the same attempt number and branch: when the environment provider says it cannot start one now, the wait counts nothing, and after an hour of it the ticket blocks with a reason that says the provider was unavailable; any other failed start counts only from the fourth in a row. The board card and `bb loom ticket` say why the ticket waits and when Loom tries again.
- A worker whose ticket stays in working longer than `agents.ticket_timeout_minutes` is ended and the ticket requeued. Time paused, in checks or in review does not count.
- A rate-limited turn is retried when the provider's window resets, at most three times, and no new worker starts until then.
- A human who archives or deletes a worker thread sends the ticket back to the queue without counting a failure.
- On a machine of its own, a turn bb stopped because it moved the machine (a `machine_maintenance` error) counts as no idle.

## Reviewers

When a ticket reaches review the plugin starts `review.approvals` reviewer threads for it, within `agents.max_reviewers` across the project (a reviewer waiting for the human's answer holds no slot), on the provider and model of `agents.reviewer`. Use a different model than the workers: a model rates its own output higher than another's. Each reviewer gets its own worktree, in the environment's `reviewer` table when the spec sets one (a lighter environment: the checks run in the worker's worktree, never the reviewer's); in a partial checkout, read any file of the reviewed work with `git show HEAD:<path>` after `loom_checkout`. Reviewers follow the workers onto machines of their own unless the `reviewer` table names another provider. A reviewer that could not start waits and tries again, as a worker does, and does not count as one that ended without a verdict; an hour of an unavailable provider blocks the ticket, and approving a pending spec version sends it back to review. The brief holds the ticket and its numbered acceptance criteria, the rubric, the pull request's text on the pull request strategy (the title and description as it will open, or in a fix round the text Loom last set beside the one the worker proposes), the scope report and check results, the diff, the findings of earlier rounds and the rules.

A reviewer has four tools and no others:

- `loom_checkout()`: the first step. It puts the exact work the ticket was submitted with in the reviewer's worktree: checked out on the project's machine, or carried as one commit with the same tree to a reviewer on a machine of its own; for a stacked ticket, as the commit it is stacked on and then the ticket's work, so `git diff HEAD~1` shows what to judge. Calling it again once the worktree has that tree changes nothing.
- `loom_note({ text, reply_to? })`: record what it checked.
- `loom_approve({ summary })`: every acceptance criterion holds and no blocking finding remains.
- `loom_request_changes({ summary, findings })`: send the ticket back. `findings` has 1 to 20 entries. Each is `{ severity, title, detail, file?, line? }`, where `severity` is `blocking` or `should-fix`, `title` is one line, and `detail` says what is wrong and how to fix it. Give a file and a line whenever you can.

Rules for a reviewer:

- Read and run anything, change nothing, commit nothing. Never push or merge.
- First step: `loom_checkout()`. The worker can move its branch, and the verdict tools refuse ("Call loom_checkout first …") until the worktree has the reviewed tree, the one named in the brief.
- Judge each acceptance criterion. Approve only when every one holds and no blocking finding remains.
- Judge the pull request's text the brief shows as you judge the code, against the rubric and the ticket, and request changes to it with a finding when it is wrong or leaves out what the rubric asks of a pull request. When the worker proposed none and the rubric asks something of the description, request changes so it proposes one with `loom_submit`'s `pr`. Do not ask for the sections Loom adds itself.
- Give exactly one verdict per round, then end the turn. A reviewer that ends its turn without a verdict gets one nudge and is then replaced.
- Loom tracks the rollout order and shows it in the pull request's Rollout section, and the brief's Rollout section says what it is. Do not request changes to keep the pull request a draft or to describe the deploy order. Never request changes for the rollout order, which is advice for the human: if it looks wrong in the spec, say so with `loom_note` or in the verdict's summary.

The plugin counts a verdict only from the reviewer thread it started for that ticket and round, so a worker can never approve its own work. One `changes_requested` verdict decides the round: the other reviewers of the round are stopped, the findings reach the same worker as a message and as a `review` post, and the ticket goes through checks and review again. Requested changes also count toward `review.max_rounds`; when they reach it the ticket blocks and the planner or the human decides. When `review.approvals` reviewers approved, the ticket is approved and waits in the merge queue.

## Merging

Approved tickets enter a merge queue, one ticket at a time per project. The plugin merges exactly the commit that passed the checks and was reviewed, never the branch tip.

- `merge.strategy = "integration"`: the plugin merges the commit into the integration branch (`merge.branch`, `loom/<slug>` by default) in a worktree it owns, with a merge commit, then runs `checks.after_merge` on the merged result. The branch only moves forward when the combined code passes. A conflict, a failed after_merge check, or an after_merge check that commits or edits a tracked file leaves the branch where it was, and the ticket goes back to its worker: a conflict names the files and tells the worker to merge the integration branch into its own branch, resolve them, run the checks and call `loom_submit`; a failed check sends the output, and so does a check that changed the branch. Either way the ticket goes through checks and review again. No new worker starts while a merge is running, so none branches from a merge that has not passed.
- `merge.strategy = "pr"`: after approval the plugin asks the worker for the pull request (`loom_pr`), unless `merge.describe = "loom"`, where it uses its template with the ticket's title, body, acceptance criteria and review summary. A title and description the worker proposed with `loom_submit`, which the reviewers judged, open the pull request, and `loom_pr` then needs only the commit message. The worker's description comes first; Loom's own sections (the pull requests it depends on, the Rollout section, the line that says who opened it) follow between `<!-- loom:begin -->` and `<!-- loom:end -->`, so Loom can find and replace them later. Loom takes those markers, and anything between them, out of the worker's text. It pushes the reviewed work to the ticket's branch as one commit with the worker's message (`merge.squash = false` pushes the branch as it is) and opens one pull request through the repo's forge, a draft unless `merge.draft = false`. The forge is `gh` unless `[merge.forge]` says otherwise: the spec's own `open` and `state` commands, or `none`, where the plugin only pushes the branch. It reads the pull request every 5 minutes, those of one GitHub repository up to 10 in one call: merged completes the ticket, closed without merging blocks it, and a requeue then opens a new one; a stacked one the forge closed because the branch it built on is gone is replaced instead (see Stacked pull requests). A pull request that merged into a branch other than its repo's base, such as a stacked one merged into the branch it builds on, blocks the ticket with a reason that names the branch and the ticket whose branch it is, because its change is not on the base; on a command forge this needs a `feedback` command that prints `base`. With `none`, the ticket is done once the remote's base branch contains the commit the plugin pushed.
- Fix rounds: on `gh`, or a command forge with a `feedback` command, the plugin also reads the pull request's checks, reviews, unresolved review threads and comments. In a repo with `ci = false` a failed check starts no fix round, though the others still do; `loom_propose` refuses a repo that relies on CI through a forge that reports no checks. Failed checks (once no pending check holds them back, or a set time after the push: Loom's `checksSettleMinutes` setting, 30 minutes by default; a check still queued 5 minutes after Loom first saw it stops holding, and so does a running check less than 75% along, by its own progress, its usual duration or its job's steps, with Loom's `checksQueuedMinutes` and `checksNearDonePercent` settings and the spec's `merge.checks_queued_minutes` and `merge.checks_near_done_percent` to change them; a commit status holds until the set time), reviews that request changes or comment with text, and unresolved threads go back to the worker as a fix round, each item once; so do top-level comments from people. Bots' top-level comments, such as plan output, do not count, and neither does anything from the pull request's author, because a worker's replies come from that account. A human reply on the ticket starts a fix round too. Each item in the fix round's message carries its key. The worker fixes what applies, answers review comments with `loom_pr_reply` (never push, merge, close, approve or edit the pull request), and calls `loom_submit`, with `pr` when the feedback asks for a new title or description. Its replies never count as new feedback: they come from the pull request's author and end with Loom's mark. A fix with no change goes straight back to `pr_open`. A fix whose only change is the proposed text goes through review, with no checks; once approved, the plugin sets the text and the ticket returns to `pr_open` with nothing pushed. Otherwise it passes the checks and a review again, the worker writes its commit message, and the plugin pushes it as one more commit on the same pull request, after checking that the pull request is still open, and then sets a new title or description. The plugin sets the text with the forge's edit on the project's machine (`gh pr edit`, or a command forge's `edit` command); a forge without one gets the text posted on the ticket for the human to set, and the briefs say so. An edit that fails with what looks like a temporary error is tried again on a later read of the pull request, unless a newer approved text replaces it first (a proposal is judged against that waiting text, so even one that keeps the description as it is goes to review and, once approved, drops the waiting edit); any other failure is posted and the pull request keeps its text; neither blocks the ticket. On `gh`, once a fix is pushed, the plugin asks the people whose reviews and review threads the fix answered to review the pull request again (not bots, and not people who only left top-level comments), and posts on the ticket anyone it could not ask; the fix stays pushed either way. A pull request that merged meanwhile completes the ticket. When someone else pushed to the pull request's branch, the plugin merges their commits into the ticket's work itself, against the commit it last pushed there, so the next push builds on them: a worker on the project's machine is told to merge them at the start of the fix round, and a worker on a machine of its own gets the merge from the project's checkout as linear commits (never fetch or merge that branch there). Commits that arrive during the fix are merged before the push, with the ticket's checks run on the result and no new review; a conflict or a failing check goes back to the worker. After `merge.max_fix_rounds` rounds started by the pull request's feedback (5 by default; 0 follows only merged and closed; the human's replies do not count, and a requeue starts the count again) the ticket blocks, and the pull request stays open. A requeue of such a ticket continues on the same pull request. After each push to an open pull request (a fix round, a catch-up, a refresh, commits someone else pushed, or a land's push to the integration pull request already open) and after it moves one to another base, the plugin runs the forge's `after_push` commands on the project's machine, with `LOOM_BASE` the branch the pull request builds on now; a push and a move in one step run them once, after the move, while a push whose move fails or waits runs them at once on the base it still has and a later successful move runs them again; they run at most once per push and once per move, even when the merge runs again after a failure; a failure is posted and pauses or blocks nothing. A forge's `ignore_checks` globs (`*` any run of characters, `?` one, everything else literal and case-sensitive, matched against the whole name) drop the checks they match from everything Loom reads, so they start no fix round and count nowhere.
- Released workers: while a pull request waits, its idle worker is archived to free its environment (unless `merge.release_workers = false`, which a pending version may change after approval), once it has nothing in flight and its worktree holds exactly the reviewed commit. It stays the ticket's worker: a fix round, the human's reply or a catch-up unarchives the same thread, bb restores its environment on its branch, and the worker gets the round with a note that files git ignores are gone. A restore that keeps failing, or one bb cannot do, hands the ticket to a new worker from the branch, whose brief names the earlier worker's thread (`bb thread log <id> --all`).

- Pull requests kept fresh: on a repo that sets `refresh_behind` (in `[merge]`, or on the `[[repo]]`; off when unset), the plugin fetches the remote base on the project's checkout at most every 30 minutes while the repo has open pull requests and counts the commits of the base each one's pushed commit lacks. An open pull request on the repo's base that lacks at least that many, or that the forge says conflicts with its base (`mergeable`), goes through the merge queue as a stacked one that must catch up does, after every approved ticket and restack: the plugin merges the base tip it counted against, with no fetch of its own, into the ticket's branch in its worker's worktree (bringing a released worker back first, or carrying the merge as linear commits to a worker on a machine of its own), runs the ticket's checks there and pushes with no new review, and posts how many commits the branch lacked. It never rebases or force-pushes; a conflict goes back to the worker with the files named. A stacked pull request takes the base through its parent's refresh, and a ticket in a fix round waits until it is back in `pr_open`. See "Keeping pull requests fresh" in `references/spec.md`.
- Stacked pull requests: on the pull request strategy, unless `merge.stack = false`, a ticket does not wait for its dependencies to merge. It starts once each dependency is done or has an open pull request with a commit the plugin pushed. A dependency in the same repo is stacked on: the worker's worktree starts from that pull request's commit (the plugin builds a merge of them when there are several, and points the branch `loom/<slug>/<key>-stack` at it), the scope check and the reviewers' diff count only the ticket's own changes from there, and its pull request opens on that dependency's branch. While two or more of its dependencies in its repo are open, its pull request waits after review; once all but one have merged, the plugin first merges the base branch into the one still open, so the new pull request does not show the merged work as its own. When a dependency's pull request gets a new commit, or merges, the plugin merges the new commit, or the remote base branch, into each ticket stacked on it, in that worker's worktree, runs that ticket's checks and pushes the result with no new review; after a merge it also moves the pull request to the base branch (`gh pr edit --base`, or a command forge's `retarget` command; on a forge with neither the post asks the human to, and a `retarget` that fails in a way not worth waiting out asks too, without pausing). A conflict, or a check that fails on the result, goes back to the worker, who merges the branch `loom/<slug>/<key>-stack` and resolves it; so does a worktree with a merge its worker began and did not finish, which the plugin leaves as it is for the worker to finish with `git commit` or abort with `git merge --abort`. A released worker is brought back to do it; a ticket whose worker the human archived is not brought up to date until a fix round gives it one. When the forge closes a stacked pull request because the branch it built on is gone, as GitHub does when the pull request it was stacked on merged and its branch was deleted, the plugin does not block the ticket: once the ticket that owned that branch has merged, or Loom has let go of that ticket's own pull request, it lets go of the closed pull request, posts why, keeps the ticket's branch, the commit it pushed there and the title and description the reviewers approved last, and the merge queue brings the branch up to date and opens a new pull request on the branch the ticket builds on now, with that text, field by field before the template, and Loom's own sections as they are now. When the dependency merged into yet another branch, which blocks that dependency, the ticket waits for the dependency's new pull request before its own opens. A closed stacked pull request whose branch is still there blocks the ticket, since a person closed it. With workers on machines of their own, stacking works the same way, but the plugin makes every merge on the project's checkout and carries the result into the worker's worktree as linear commits; a conflict arrives with conflict markers in its files, and such a worker is not released while a dependency in its repo is open (see "Stacked pull requests on new machines" in `references/spec.md`). A dependency in another repo cannot be stacked on: its dependents start on its open pull request, their brief says how to read its files, and each new commit on it is posted on the dependent ticket and sent to its worker while it works.

Under the integration strategy, and on the pull request strategy with `merge.stack = false`, a ticket that depends on another starts only after it is done. If git, the repo's forge or the remote is missing, or the integration branch is checked out in another worktree, the plugin pauses the project and says why in `bb loom show`; fix it and `bb loom resume`. A failure that looks temporary does not pause it: a call to the project's machine that got no answer (it ran out of time, or the machine's Loom worker exited, as during a plugin update), a server error, a rate limit, a timeout or a network failure, from `gh`, `git` or a command forge's `open`, `state` or `feedback` command. A merge step that fails that way keeps the ticket in merging and runs again after 1, 2, 5 and 10 minutes, then every 15 (at least 15 after a rate limit, or the time the server names); the merge queue waits with it, the ticket gets one post, its card, its page and the next-step bar say when Loom tries again, and the project pauses only after an hour of failures, with a reason that names the ticket, the error and how long. A merge the plugin put in a worker's worktree is kept until its checks pass, so the next run finishes it and nothing is pushed before then; asking for reviews again and `after_open` and `after_push` commands are not tried again, and their failure is posted once. The human can block or cancel a ticket whose merge waits; on the integration strategy the plugin first takes an unchecked merge back out of the integration branch. Reading the diff for reviewers waits the same way. Reading an open pull request waits on its own steps, whether the read went through `gh` or through a command forge's `state` or `feedback` command that failed or timed out, and a call to the project's machine that got no answer counts as a server error. A server error (HTTP 500, 502, 503 or 504), a timeout or a dropped connection does not pause the project: that pull request's next read waits 5, 10, 20 and then 30 minutes, the ticket gets one post when the failures start, and the project pauses only after an hour of failed reads, with a reason that names the pull request, the error and how long it lasted. A network failure, such as a host name that does not resolve or a connection that cannot open, stops every read to that host (for a command forge, the pull request URL's host), in every project, for 5, 10, 20 and then 30 minutes. One failed call counts once however many pull requests it asked for, the first ticket gets one post, and the project pauses only after an hour with no read to the host working, with a reason that names the host, the error and how long it lasted. A rate limit stops every read to that host, in every project, for 15 minutes, doubling to an hour while the limits go on (longer when the forge names a later time), and never pauses; the ticket gets one post per backoff. Any other failed read still pauses the project, such as a missing login, a pull request the forge cannot find, or a command that exits 0 without printing a state or its JSON object. The ticket page's next check time shows the wait. The human can read the open pull requests now with `bb loom sync <slug>` or the page's Sync pull requests: it goes past a ticket's wait after failed reads and a host's network wait, keeping their streaks, but not past a rate limit, and writes no `human.action` event. A merge left half done resumes without a second merge commit or a second pull request.

To test a repo's forge against a live pull request, `bb loom forge check <slug> <KEY or url>` makes the read a poll makes, on the project's machine: gh's batch read, or the spec's `feedback` command, else its `state` command. It prints what Loom reads (the state, draft flag, review decision, base and whether it is mergeable, each check with its state, and each item with its kind, author, key and first line), or why the read failed, how a poll treats that failure and each field the host contract refused, with zod's message. `--repo <name>` names the repo of a pull request URL on a multi-repo project, and `--version N` uses that spec version's forge, so a pending version's forge commands can be tried before the human approves it. It changes no ticket and writes no event, so planners may run it too.

## Deploy order

Loom orders three things: `depends_on` orders the work (when a ticket starts), `merge_after` and stacks order the merges, and a ticket's `rollout` orders the deploys: when its change may reach traffic and what must be live first. Only the pull request strategy has deploy order; `loom_propose` refuses it on the integration strategy, where every ticket lands together. Deploy order is advice for the human: Loom never holds, delays or reorders a start, a review, a merge or a push because of it, and posts nothing to the forge for it apart from the pull request description's Rollout section. When a ticket or milestone an open pull request requires goes live, or stops being live, the plugin rewrites that Rollout section on its next read of the pull request (`gh` reads the description in its poll; a command forge's `feedback` command may print `body`), replacing only what lies between Loom's markers and never cutting the description short. Without the description, without exactly one pair of markers in it, when the new section would make it longer than a pull request takes, or on a forge without an edit, it leaves the pull request alone and says so once on the ticket; the Rollout tab stays the source of truth. `references/spec.md` has every field.

- A ticket's rollout status runs from not merged to merged, live and soaked, apart from its ticket state. A ticket in a repo whose `deploy.on_merge` is true is live once its pull request merges. A merged ticket with `verify` is live once that command exits 0; Loom runs it on the project's machine, in the ticket's repo checkout, every 15 minutes with a 2-minute timeout. A milestone's `check` runs the same way from when the project starts. A failed run, the machine away included, is kept on its row and tried again at the next interval, and never pauses the project. One command runs per target at a time, across a plugin reload too, and a run keeps no result when the project was archived or the ticket's `verify` or the milestone's `check` changed while it ran. Loom keeps checking after the project is done, until it is archived. Anything else waits for the human's Mark live on the Rollout tab or `bb loom live`.
- Going live writes a `rollout.live` event, and the human's undo a `rollout.unlive` event. A check's last result stays on its row and writes no event. An undo of a deploy-on-merge ticket stays until the human marks it again; a verify or check that passes marks it live again.
- The description Loom opens a pull request with, the worker's or its template, gets a `## Rollout` section when the ticket has a rollout or the project has stages.
- The Rollout tab and `bb loom rollout <slug>` show the next safe step (the earliest stage with steps not live, and in it the steps whose requirements are all live, after the stage before has soaked), the warnings, each stage's steps and the milestones and windows. A planner reads the order with `bb loom rollout`, changes a ticket's rollout with `loom_edit_ticket` (a patch of `rollout` alone changes a ticket whose pull request is open, or a done one), and adds stages, milestones and windows in a new spec version.

## Landing

`bb loom land <slug>` is the human's step on the integration strategy. It pushes the integration branch and opens one pull request to the base branch, with the project's goal and the merged tickets in its description (a draft unless `--ready`, titled with `--title` or the project name). Running it again pushes the new commits to the same pull request. It refuses while a ticket is merging or when no ticket is done yet. When every ticket is done or cancelled the project is done. `bb loom land <slug> --direct` lands with no pull request instead: it waits while a worker's worktree is still being created, fetches the base branch from the merge remote into Loom's own worktree, merges it into the integration branch when it moved (refusing on a conflict, with the files), runs the `after_merge` checks on the result (refusing and resetting the branch when one fails, with its output), and pushes to the base branch without force. No new worker starts while it runs, and block and cancel wait for it. `--title` and `--ready` do not go with `--direct`. On the page, "Land to <base>" beside Land does the same. The plugin pushes to the base branch only when the human lands with `--direct`, and nothing is pushed on the integration strategy until the human lands. Agents never push, merge or land: tell the human to run `bb loom land`. When a project finishes, Loom sends its record, or an agent's summary of it, to the done hook the human set in Loom's settings; agents never run `bb loom report --send`.

## Multi-repo projects

A spec with `[[repo]]` tables spans several repositories, each a bb project with a checkout on the project's machine (the machine the planner ran on). Every ticket names its repo and changes only that repo; its scope, verify commands and protected paths are relative to the repo's root. `references/spec.md` lists the `[[repo]]` keys and has an example with two repos.

- Start: `bb loom start` creates the integration branch (`merge.branch`, the same name in every repo) in each repo's checkout, from that repo's base. When a repo has no checkout on the project's machine it refuses, leaves the project ready and names the command that clones it: `bb project source add <id> --clone --machine <host>`.
- Workers: one worker per ticket, in a worktree of its ticket's repo, branched from that repo's integration branch (or from its remote base on the pull request strategy). The brief names the repo and lists the other repos with their checkout paths, to read and never edit; on the integration strategy their merged work is on the integration branch, readable with `git -C <path> show <branch>:<file>`. Scopes collide only within one repo, so tickets in different repos run side by side.
- Checks and review: the plugin commits and runs the checks in the ticket's repo: the ticket's verify commands, then the repo's `checks`, or `checks.commands` when the repo sets none. Protected paths are `scope.protected` and the repo's own `protected`. Reviewers get a worktree of the ticket's repo, and their brief lists the other repos with their checkout paths, as a worker's does.
- Merging: each repo has its own integration branch and its own Loom worktree. The merge queue still runs one merge at a time per project, across every repo, and `after_merge` runs on the repo's merged branch (the repo's own list, or `checks.after_merge`). On the pull request strategy each ticket's pull request opens in its repo, on that repo's remote and base.
- When a merge, a review or a pull request poll finds a repo without a checkout while the project runs, the plugin pauses the project with the clone command in `bb loom show`; clone it, then `bb loom resume`.
- Land: `bb loom land <slug>` lands every repo with a done ticket, in the spec's order, each with its own pull request to its own base; `--repo <name>` lands one repo, and `--direct` pushes each repo to its own base. The first repo that fails stops the land: the repos before it stay landed, and the error names the repos still to land and the command to run again. The project is done when every ticket is done or cancelled and every repo with merged work has landed since its newest merge.
- Changes tab: on the Loom page the Changes tab has one section per repo, in the spec's order and headed by its repo chip. Each section has that repo's integration branch compared with that repo's remote base branch (`<remote>/<base>`), what each of its merges added, and its tickets not merged yet; on the pull request strategy, its tickets compared with that repo's remote base. The panel on a repo's branch lands that repo alone ("Land <repo>" and "Land <repo> to <base>", like `--repo <name>`), and a repo that cannot be read, such as one with no checkout on the project's machine, says why in its own section.
- Record and done hook: the record (`bb loom report`) lists each repo with its bb project, base and integration branch, then one outcome line per repo (the pull request it landed as or the base it was pushed to, the merged work it has not landed yet, or no merged work; on the pull request strategy, its tickets' merged pull requests and the ones still open), and names each ticket's repo. Besides `LOOM_PROJECT_SLUG`, `LOOM_PROJECT_NAME`, `LOOM_PROJECT_KEY` and `LOOM_RECORD`, the done hook gets `LOOM_PROJECT_URLS`, every repo's landed pull request, one per line in the spec's order, and `LOOM_PROJECT_URL` is the first of them, the first repo's pull request when it has one. A repo that never opened a pull request, such as one landed only with `--direct`, has no line.
- Reading: `bb loom show` lists each repo with its bb project, base, integration branch, pull request, when it last landed and whether it has merged work to land; `bb loom tickets`, `bb loom ticket` and the planner's `loom_board` show each ticket's repo.
- Revisions: after approval a new spec version may add `[[repo]]` tables, but never removes, renames or moves an approved repo to another bb project, base or remote.

## Blocked tickets

A ticket blocks when its worker calls `loom_block`, when it fails `max_attempts` or `max_check_failures` times (checks run after a merge count too), when reviewers asked for changes in `review.max_rounds` rounds, when its reviewers ended without a verdict, when its pull request was closed without merging (unless it was a stacked one the forge closed with the branch it built on), merged into a branch other than its repo's base, or needed more than `merge.max_fix_rounds` fix rounds, or when the human runs `bb loom block`. When bb refuses to start its worker or a reviewer with a client error (an HTTP 4xx status other than 408, 409 and 429), it blocks at once, with "bb refused to start a worker:" or "bb refused to start a reviewer:" and bb's message as the reason. It gets back into the queue in one of two ways:

- The human answers on the ticket (`bb loom post <KEY> <text>`) and runs `bb loom requeue <KEY> [--note <text>]`, or `bb loom requeue <KEY> --review` to send it back as it is (below). A reply on a blocked ticket also goes to the planner at once, as a message that starts with "[loom] The human replied on <KEY>, which is blocked", with the reply as its detail; the planner reads the ticket with `loom_ticket` and answers with its board tools.
- The planner answers in a triage round (below) with `loom_post`, `loom_edit_ticket`, `loom_add_tickets` or `loom_cancel_ticket`, and requeues with `loom_requeue`.

A requeued ticket starts a fresh worker on the same branch, and the brief carries the whole thread, so it continues where the last worker stopped. Requeueing resets the failure counters and gives the ticket `review.max_rounds` fresh review rounds.

Review again as is (`bb loom requeue <KEY> --review`, `loom_requeue({ key, note, review: true })`, or Review again as is on the ticket page) sends a blocked ticket back with no new worker, when the work is right and only needs to be reviewed or followed again, such as after reviewers that ended without a verdict or a status no fix can clear. Loom reads the ticket's branch on the project's checkout first. When the ticket has a pull request Loom pushed to and the branch has nothing that pull request lacks (the same tree as the commit Loom last pushed), it goes straight back to `pr_open`, as a fix with no change does, and its fix rounds count from 0 again. Otherwise, when the branch is still the commit whose checks passed last (the newest check post passed, at the ticket's head), it goes back to review for that commit in a new round, with the counters reset as a requeue resets them. Anything else is refused with the reason, such as a branch with changes since that commit or no commit that passed its checks, and a plain requeue is the way on. Blocking ended the ticket's worker and reviewers. On the pull request strategy the worker's thread, when Loom ended it for the block or a release, becomes the ticket's released worker again: the pull request's next fix round, or a catch-up with a dependency it is stacked on, brings the same thread back, or a new worker from the branch when bb cannot restore it. A stacked ticket whose worker's thread cannot come back, because the human archived it or it ended for failing, is refused while a dependency it is stacked on is still open, since nothing could bring its branch up to date. Requested changes go to that thread as well, and to a new worker from the branch when it cannot come back; the note, when given, is a reply on the ticket.

When the human approves a pending spec version, the plugin itself requeues every blocked ticket whose worker never started (bb refused it, it failed to start `max_attempts` times, or its environment provider stayed unavailable for an hour). A ticket blocked because bb refused its reviewer, or because no reviewer could start while its provider stayed unavailable, goes back to review instead, in a new review round for the same commit, because its work already passed the checks. On the pull request strategy its newest worker thread becomes its released worker again, as with Review again as is, so requested changes, or once its pull request is open a fix round or a catch-up, bring that thread back. The plugin then sends the planner a message that names the version, the tickets it requeued or sent back to review, and the tickets still blocked. Requeue the ones still blocked with `loom_requeue` only when the new version fixes what blocked them.

Each `provider` in `[agents.worker]` and `[agents.reviewer]` must be a bb provider id, such as `claude-code`, `codex` or `pi`, not a model name such as `claude`. `loom_propose` checks them against the providers bb has and refuses an unknown one with the ids bb has; when bb's list cannot be read, the spec is accepted unchecked.

## Triage rounds

When a ticket blocks, the plugin sends the planner thread one batched message, but only when the planner is idle and no earlier round is still open. It names the board counts and, for each blocked ticket, its key, title, reason, what the worker needed, the attempt counts and the last three posts. A round also goes out when the plugin paused the project for its token budget or deadline, which a new spec version can change. Any other automatic pause, such as a forge or host error, sends the planner no round: the planner could only ask the human to resume, and the next-step bar already tells the human why and offers Resume.

The planner answers only through its tools; the human reads the board, not the planner's chat:

- `loom_board({ state? })`: the board, one line per ticket.
- `loom_ticket({ key })`: one ticket with its whole thread.
- `loom_post({ key, text, reply_to? })`: answer on a ticket.
- `loom_requeue({ key, note, review? })`: send a blocked ticket back to the queue after answering; with `review: true`, review again as is (see Blocked tickets).
- `loom_edit_ticket({ key, patch })`: change a queued or blocked ticket (title, body, acceptance, verify, scope, depends_on, merge_after, priority, repo, rollout; only the fields in the patch change). A patch of `merge_after` or `rollout` alone changes a ticket whose pull request is open, and `rollout` alone a done one too; `rollout` replaces the ticket's whole rollout, and `rollout = {}` removes it. On a multi-repo project, `repo` moves the ticket to another repo only while it has no branch, because a branch lives in one repository; otherwise cancel it and add a new ticket in the other repo.
- `loom_add_tickets({ tickets })`: add tickets, for example to split a blocked one or add a dependency. depends_on may name refs in the batch or tickets already on the board, and so may `merge_after` and a rollout's `requires_live`, which may also name the spec's milestones. On a multi-repo project every new ticket sets `repo`, and its scope and verify are checked against that repo's protected paths and checks.
- `loom_cancel_ticket({ key, reason })`: cancel a ticket; a live worker is stopped.
- `loom_ask_human({ why, steps })`: what the human has to do, as steps in order, each `{ action, version?, key?, text }`: `approve` with the version that waits, `requeue` or `reply` with the ticket key, `start`, `resume`, `land`, or `other`. The Planner tab shows them under Needs you with a button for each and checks a step off when the human takes it. Each call replaces the earlier asks; no steps clears them. A step the human could not take now (a version that does not wait, a ticket of another project) is refused.

The planner never starts, pauses or approves a project, and never edits the spec after approval except by proposing a new version for the human to approve.

## The Loom page

The human starts, watches and steers projects from the Loom entry in bb's left navigation. A first visit shows a guide to how Loom works, which "How Loom works" opens again at any time. New project shows bb's own new-thread composer and a repo picker: bb's standard projects besides the composer's own, filterable by name, up to 10, each marked "no checkout" when no machine has a checkout of it. The picked repos go to the planner as a starting point, not a limit; it can add others and offers to clone a repo without a checkout. The composer's submit starts a planner thread with the `loom-plan` skill, and the page then shows its Planner page under the Plan stage; once it proposes, the conversation is that project's Planner tab. Conversations that have not proposed a spec yet are listed on the home page until their thread is archived. The home page shows tiles across every project and one table of every project and planning conversation. Its "Needs you" column has a button for each thing that needs the human in that project (a blocked ticket, a draft to review, a pending spec version, a finished integration project to land, a project Loom paused by itself), and rows that need the human come first with a coloured edge; the table also shows each project's state, progress, live agents, throughput, tokens and the reason the plugin paused it. A search box filters it by name, key, slug or title, and done and archived projects that need nothing fold into a remembered "Finished" group. A project with an approved spec shows a health strip (progress, pace, token budget, deadline and capacity) above its tabs, and every project shows a next-step bar under its header: the stages from Plan to Land, one sentence on what happens next and one button, yellow when tickets are blocked or Loom paused the project. On a multi-repo project, a repo chip marks each ticket's repo on the board, the ticket page and the Spec tab, whose settings list the repos and whose Files view groups paths by repo, the header links each repo's pull request, and the land buttons name the repos they land ("Land to each repo's base" when the bases differ). The Board tab counts the blocked tickets, the Spec tab carries a badge while a draft or a pending version waits for the human, the Planner tab shows "?" while the planner waits on a question and otherwise counts the steps it asked for that are not done, the Changes tab counts the files of a project ready to land that the human has not marked viewed, the Merge order tab counts the pull requests with nothing before them, or turns red for one that merged into another ticket's branch, and the Rollout tab counts its warnings. Under the header, an About strip shows the spec's summary (the goal's first paragraph for a spec written before summaries were required, and the waiting version's summary while one that writes or changes it waits for approval), the issues and pull requests the goal links to, Done when, Full goal and the planner's thread; the home table shows each project's summary under its name. The tabs are a Board (a row per stage stacked down the page: Needs you with the blocked tickets, In progress with Working, Checking, Review and Shipping, Up next with Ready and Waiting, and Finished with Done and Cancelled folded; each card has its age, attempt, review round and thread link, and a waiting ticket says what it waits on; before approval, the draft's tickets as dashed cards), Agents (every thread with its ticket, model, running time, timeout, tokens and how it ended), Insights (how the project went in a headline, a few sentences and four figures; a chart of when the work happened, where a click or a drag across bars shows only that stretch, with Whole project, Latest run and Last 24 hours; What happened, a group per run and pause with one entry per ticket that says what happened to it there and its steps one click away, a Right now list of blocked tickets, open pull requests and tickets a pause holds, and Problems, You and Every event filters with a search box, where an action that wrote several events reads as one line; and the numbers beside it: how long a ticket takes, where its time goes, how often the first try is right, what it cost, when you stepped in, what went wrong and the checks by command; on the pull request strategy it times a ticket to its pull request and counts the wait on people after it separately, which changes nothing about how Loom schedules or merges), the Spec as one page (How it runs: the settings as cards; ## Metrics

`bb loom metrics <slug>` prints the project's numbers, and `--json` prints them for you to read. They come from the plugin's append-only event log, so they are exact except for tokens. `--days N` (1 to 90) sets the window for throughput and cumulative flow; the other numbers cover the whole project.

- Flow: work in progress (tickets in working, checking, review, approved, merging or pr_open), throughput (tickets done per UTC day over 14 days), cycle time (first move to working until done; p50 and p85), lead time (creation until done) and work item age (time in flight, oldest first).
- Agents: first-pass approval (of tickets with a verdict, the share approved with no changes requested in the first verdict round), review rounds per done ticket, how many check posts failed, how many times a ticket blocked, and human interventions (commands the human ran, apart from `start` and the approval of a draft).
- Tokens are sampled about once a minute per live thread and once when it ends, so a thread's last minute can be missing. Report them as approximate. Some providers report no token usage at all: `tokens.unreported` counts those threads, and their tokens are missing from the totals.
- Cumulative flow is the count of tickets in each state at the end of each of 14 days; a ticket counts as queued from its creation. Active time is how long the project ran, without paused spans; `windowActiveMs` is the part of it inside the window, and the health strip's pace is the tickets done in the window over that time.
- Where the time goes: `timeInState` sums, over done tickets, the time spent in each state from creation until done, and `flowEfficiency` is the share of it spent working. `checksByCommand` lists each check command's runs, failures and p50 duration ("scope check" and "worktree check" are the plugin's own refusals), and `scopeFlags` counts check posts with files outside the scope or on protected paths.
- Review and cost: `findings` counts review findings by severity over the reviews with a verdict, with the rounds and the rounds that requested changes. `tokensByTicket` is the 5 tickets that used the most sampled tokens. `reliability` counts failed worker attempts, rate-limit retries, worker timeouts and merges sent back to work.

Use the numbers to say where work piles up: a growing queue means too few ready tickets or workers, a growing review lane or a large share of time in review means reviewers are the limit, and a low first-pass approval, many blocking findings or one check command that fails often mean the briefs or acceptance criteria need work.

## Rules for agents

- NEVER run `post`, `block`, `requeue`, `cancel`, `approve`, `start`, `pause`, `resume`, `archive` or `land` from a Loom planner, worker or reviewer thread. They are refused with `loom_human_only`. When the human needs to act, say which command.
- A worker works only in its worktree, never pushes or merges, never edits a protected path, and never runs `bb loom` commands other than the read commands. A reviewer changes nothing and commits nothing.
- Read commands (`list`, `show`, `spec`, `tickets`, `ticket`, `metrics`, `feed`, `forge check`, and `report` without `--send`) are fine for everyone. `forge check` runs the repo's own forge commands (gh, or the spec's `feedback` or `state` command) on the project's machine, as a poll would, and changes nothing in Loom.
- Do not edit the plugin's database or work around a refusal. If a state looks wrong, tell the human.
- The spec format, defaults and the list of errors and warnings are in `references/spec.md`.
