# Steer replay and backend probes

Run `npx vitest run test/server` from `plugins/tavern`. Most backend tests use in-memory SQLite and a fake journal port. The exhaustive RPC test instead boots the real server and journal against temporary SQLite and files. SDK requests pass through an audited local proxy; registered RPCs use the installed SDK’s official schema and strict-JSON driver. No provider threads are started.

## Two-goal replay

Start a Keeper manually after integration and give it two harmless, private goals named Vault cutover and Proxy retry. Do not use real production work for this check. Save their initial plan versions. Send these messages while the party continues working:

| Message | Read as | Expected plan change |
| --- | --- | --- |
| Vault: stage first | steer, Vault | Vault only |
| What is waiting? | question | Neither |
| Look up lunch menus | aside | Neither |
| Proxy: retry only once | steer, Proxy | Proxy only |
| Which model checks it? | question | Neither |
| Vault: keep the rollback | steer, Vault | Vault only |
| Check the weather | aside | Neither |
| Proxy: stop the extra rollout | steer, Proxy | Proxy only |
| What is the ETA? | question | Neither |
| Vault: test staging again | steer, Vault | Vault only |

After every message check that the reply is short, the routing tag names the right quest, and only a steer creates a plan version. Check that an aside helper has no board-quest or waypoint link. The automated replay uses fake tools to enforce these database properties; it does not prove the model consistently chooses the correct route.

## Tale data and Keeper holding state

`tale.test.ts` exercises tale and credit reads through the strict RPC host. Board-quest detail supplies optional `tale` and `memberCredits` fields. The tale comes from the latest indexed `quest.wrapped` event, including when it lies beyond the generic event page. New wraps snapshot skipped waypoint reasons; old wraps reconstruct only the matching plan's skip receipts before that wrap. Blank or missing `left` becomes null, and cellaring retains the story.

Member credits are distinct waypoint ids derived from completed linked journal entries and verification receipts, not symbolic plan owners. Only reported or verified waypoints count as made; only fully verified waypoints count toward a checker's credit. Released unfinished work and unknown identities get no named-member credit. Explicit `review.actor` wins over later note authors. The legacy `updatedBy` fallback rejects known non-Warden note authors; historical actor ids without a remaining member record stay available on the waypoint but never create named-member credit. The UI provides class-only fallback labels when identity cannot be proved.

Room Keeper rows carry optional `threadTitle` and `threadCreatedAt`, captured from bb thread DTOs through lifecycle/native observation and cold reconciliation. The RPC emits null until metadata is observed; it never substitutes the Tavern binding time, a character name or `titleFallback`. A title-only observation invalidates the room without adding Keeper news. Room reads make no metadata SDK calls, and older payloads may omit both fields.

The shared `extractReportHeadline` supplies legacy display headlines without changing reports. It accepts optional read-only maps of thread names, quest short titles and waypoint titles. Known ids are replaced as whole tokens; unresolved ids or labels containing ids return no headline. Stored headlines pass the same guard. The existing verdict and sentence rules retain file names such as `README.md`, and the 160-character limit applies after replacement. The Vex receipt for `quest_c4151d86-1feb-4271-a91c-0f66c285047e` is a pinned regression; full reports retain their original text. `nameReportIds` exposes the same replacement step for whole outcomes and evidence: it preserves whitespace and length, leaves unresolved tokens in place and returns their unique ids in encounter order. Tokens touching a slash or backslash are path references, so both helpers leave them alone rather than treating a worktree directory as a person.

Reports accept an optional trimmed `headline` of at most 160 characters. Classes and the Keeper guide request one plain sentence stating the answer; full outcomes and evidence remain unchanged. Headline changes participate in report deduplication. Warden headlines cannot claim independence, and same-family headlines retain the server's limitation within that limit. Old reports remain sparse. The real-entrypoint sparse-record fixture checks the new tale shape as strict, lossless JSON as well as all 40 registered methods.

`heldAt` measures a tick delay, including cooldown or a busy conversation; it is not evidence that the user is still typing. Room and decor now use the current typing/after-message window. A sweep invalidates expired cached status once, without clearing `userAt`, which orders delayed manual-Stop events. An idle tick with no packet clears its orphaned hold. Host archive observations persist the separate sparse-safe `archived` flag, clear hold timestamps and refuse typing pings; archived Keeper rows and their uncellared quests remain in room data for the page to fold. Unarchive and cold reconciliation refresh the observed flag. Manual Stop alone is not archival.

## Decision acknowledgement and history

`decision-seen.test.ts` covers server-persisted, optional `seenAt`, cross-runtime token Undo, same-clock stale Undo, atomic rollback, sparse records and shared attention predicates before the page limit. Room, decor and Ledger return the same capped attention list with uncapped `decidedCount` and a `decidedThroughId` snapshot. Returned and stopped quests stay in attention until seen or sent to the cellar. A scoped or global bulk acknowledgement can pass that snapshot as `throughId`; decisions inserted after the rendered snapshot stay unseen, including at the same clock time.

`markDecisionsSeen` returns only the ids it changed and a durable `undoToken`, or null when nothing changed. `markDecisionsUnseen` clears only that batch's still-current acknowledgements. Neither operation undoes the business decision, changes Keeper memory, resumes a stopped Keeper, emits agent news or sends a tick. Both invalidate the affected thread, room and quest views. The UI calls the archive the cellar; internal archive fields and RPC names do not change.

Ledger and board-quest detail carry the first 100 decisions, newest first, including seen, undone and cellared history. `decisionsTotal` and `decisionsNextCursor` expose the remainder through `decisionHistory`. History cursors bind the Keeper, optional quest and stable insertion position, so acknowledgements and newer arrivals do not reshuffle older pages. The strict real-entrypoint fixture exercises all three new RPCs with optional fields absent.

## Logic-review fixes

The server regressions now use bb 0.49-shaped dispatch contexts. Queued rows carry `content`, their own author and plugin origin, stable ids and creation times. Grouped contexts use the first row's origin and summarize the authors. Retries are system-authored. The installed declarations define these queued-row fields at `bundled-types/bb-plugin-sdk.d.ts:4610-4782`; the authoring reference above documents the inline pass, repeated drain passes, and `message.queued`, `message.dispatched` and `message.cancelled` announcements.

- A user message has user authorship and neither a plugin origin nor a sender thread. Classification happens per queued row. Plugin ticks, journal notes, nudges and spawn briefs are not user messages.
- User receipts pair inline attempts with stable queued ids. An unmatched busy-thread receipt pairs in FIFO order even when queue creation is delayed. Otherwise pairing uses thread, exact text and a five-second creation-time window. This window is a correlation heuristic because the SDK provides no inline message id; it is not an SDK uniqueness guarantee. Identical user messages remain distinct. Queue announcements attach ids early, and cancellation clears the matching pending route.
- Pending messages never block a tick. A digest states `Not yet routed` and the message text. Accepted pending messages expire when their following turn ends, including a failure before an active lifecycle transition; `route.missed` remains in the audit log. Messages still waiting in the queue do not expire with the preceding turn.
- Tick ids and payloads are stored before sending. Reports and the event cursor move only after a sent result or a queued dispatch announcement. Cancellation leaves facts unread. Startup and later sweeps reconcile uncertain sends against queued rows and `client/turn/requested` history, with a persisted sequence watermark. This is recovery and deduplication, not a distributed transaction with core.
- Digests read events oldest-first, page at 100 rows and include typed report outcomes and ask answers/defaults. Churn alone and the Keeper's own actions do not wake it. Overflow remains unread; a fact larger than one digest continues in the next tick and is not marked complete early. `tavern_status` now pages events, asks, reports and pending routes, and reads full reports and original briefs by report id and character offset.
- Each Keeper and each default are isolated from other failures. A missing Keeper is stopped. An error-state Keeper can receive its re-anchor. Journal `quietSince` prevents a stale strike against recent checklist progress, and member output does not cause SDK history reads or view invalidations every second.
- Done maker reports require completed or verified linked entries with evidence. Wardens are stored as checkers and receive no linked entry. The roll-up ignores legacy Warden-owned entries and exposes rejection reasons.
- Explicit aside and new-quest choices are enforced. Only `decision` asks with explicit `reversible: true` may carry timers; the declaration is persisted and checked again when applying the default. Greenlit class counts cap later hires, including reservations; a same-party re-plan is recorded as a reversible decision, while a party expansion opens a new approval. Approval is recorded on the card, not inferred from chat. Only active members and in-flight reservations occupy the approved class allocation; done, stopped and failed members free capacity. Each party slot permits its initial assignment and at most two replacements per plan version. Slot counters are persisted across reloads, and each successfully settled replacement is a reversible Keeper decision under “Decided for you.” Refused attempts record no replacement decision; uncertain delivery waits until recovery finds the real child. A new plan version starts a fresh replacement budget without expanding the approved class counts.
- The two installed migration statements remain byte-for-byte unchanged. Tests pin their positions and SHA-256 hashes, then apply appended migrations to an existing database and verify metadata backfills and the immutable audit log. New SQL is only at the end of `APPENDED`.
- Class and voice rules precede capped data blocks. UTF-8 limits preserve whole characters. Reports, briefs, titles and ledger text are quoted as data. A journal or registry failure cannot make configuration throw and remove the role's tool selection.

The review's diagnosis is accepted. Its proposed waypoint-level approval restriction was not added: the coordinator explicitly chose a per-class staffing boundary, so a same-party re-plan can change waypoints without another card. The journal still rejects its own stale agent-only notes at admission; ordinary user messages and mixed groups are not deliberately rejected by Tavern apart from a new start naming an unknown class.

## Scope integration

## Integration notes

- The registry RPC accepts an optional `projectId`. Existing `{}` calls remain valid and return shipped and global definitions. UI callers that need project-local classes must pass the current project id. Mention search already does this before class binding.
- Project class overrides are trusted role instructions, not inert documents. A checkout's `.agents/tavern/classes/keeper.md` can change its Keeper's instructions and permission settings; inspect overrides before starting a class in an unfamiliar checkout. Character style text is quoted data and cannot change role authority.
- Project registry overrides are read only from a server-local checkout. A project available only on another machine returns an explicit registry problem rather than reading that machine's path on the server. Remote override loading through `sdk.files` remains future work.
- Smiths receive managed worktrees for Git checkouts using the host's legacy selection or the `git-worktree` provider. Other environment providers reuse the parent environment. A provider-specific worktree adapter is not inferred from its name.
- The RPC caller context distinguishes plugins from clients, but does not distinguish a human from an agent (`bundled-types/bb-plugin-sdk.d.ts:155-165`). The user-facing ask endpoints therefore are not a security boundary proving human consent. Tavern never performs production writes, sends-as-you, merges or deploys from those answers. Those operations must still use the user's explicit approval process. The CLI refuses ask answers when invoked with agent thread context, and agent tools cannot fabricate `source: user` decisions.
- The shared contract additions from the UI builders, `reports` and `saveCharacterVoice`, have server handlers. Voice saves validate presentation fields and atomically write the global character override.

Gate contact is keyed by waypoint id and the outside owner's identity/title/done-when, not a plan version; legacy version-keyed rows are matched against their original plan. Unscoped promises collapse after 24 hours past due or three days without a due time, but remain readable through notes status history. Review-budget exceptions expire after one day. Every quest retains a header and status pointer under size pressure; assumptions move to status and urgency outranks recency. Global Tavern pause holds ticks, admission/recovery and automatic failure blockers; unpause requests one full ledger.

Initial briefs are spawn input retained by core, not a second send after creation. Scope approval gates the original queued row. Explicit later re-briefs remain durable, keep their slot while pending even if the child fails, and retry with backoff; five attempts open a retry/release blocker. Scope approval is persisted before the held first turn is allowed. By-size approval remains opt-in: exactly one party slot, declared reversibility, no unresolved asks/questions and no outside/user gates. Undo returns that exact approval to awaiting greenlight and releases members that have not reported.

Keeper state is persisted in Tavern, not reconstructed from a compactor's summary. Route tools require an explicit notes array on every route kind. Facts retain user wording and optional expiry; commitments require a due time or condition; waiting-on-user notes preserve hand-backs. Overdue commitments emit one durable promise.due fact. Completing a note records the outcome; wrapping or stopping closes the quest's promises and hand-backs. The Ledger RPC exposes notes, notesTotal and current-plan gate contacts, and boardQuest includes its own notes and gates.

Configure and ticks share a durable content-hash version and a dated, fenced plain-text snapshot. The copy with the highest ledger version wins, whether configure or tick. A tick that is being sent anyway includes the full snapshot on re-anchor, changed content or when its last full snapshot is ten minutes old; otherwise it carries the unchanged version and priorities. The clock never starts a tick. An outside gate gets at most one dedicated reminder when its dependencies become met; unasked gates also remain facts in ticks sent for real news. Unparseable calendar wording is retained and conservatively prioritized, not silently guessed as a duration. Manual Stop persists a quiet flag across reload. Plugin notes, queue announcements and rows created before Stop do not clear it. Provider handoff transfer is deliberately not implemented.
