# Lasting character service records

A character earns a lasting service record when a board quest returns or finishes stopping. Archiving threads or cellaring the quest changes nothing. Deleting a thread keeps its earned counts and dates but removes that thread's links from the record and its private proof receipts. No replacement thread is created.

## What counts

- Makers earn distinct verified waypoints, not journal entries, reported-done work, turns or time. The maker quest count is the number of quests with a verified contribution.
- Wardens earn checks with an unwithdrawn recorded verdict. A batch verdict on several entries of the same waypoint counts once, not once per entry. Its recorded posture distinguishes independent, same-family and not-established checks. Known matching maker and checker model families can never count as independent.
- A catch belongs to the Warden who rejected the work. It requires that exact unwithdrawn rejection, a subsequent maker-done submission with new evidence, and an unwithdrawn Warden verification. Repeating the old evidence, reversing a rejection without a new submission, or leaving a fix unverified earns no catch. The verifying Warden need not be the rejecting Warden.
- Keepers have their own returned and stopped quest counts and the number of verified waypoints across those quests. `keeper.verifiedReturns` counts returned quests whose Keeper credit contains at least one verified waypoint: an all-skipped return or a stopped quest never qualifies. Legacy verified maker totals can establish a conservative lower bound when old journals are gone; overlapping totals are never added to invent a larger Keeper result. Leading the work does not masquerade as making it.

Roles without earned records are absent rather than a collection of zero counters. Names and quest short codes are captured at completion, so archived quests still have a readable history.

## Proof and the backfill boundary

Each successful journal verify or reject writes a private attribution receipt in the same database transaction. It preserves the entry identity, maker and checker character, known model families, recorded independence, evidence and time. The service record itself is written once per terminal quest, in the completion transaction. Neither operation creates an agent-visible event.

Undo marks the original receipt withdrawn without deleting it; Redo restores it. Both changes commit with the journal history. Once the terminal record exists, linked review Undo and Redo are refused rather than rewriting the snapshot.

An accepted follow-up brief reopens finished linked work. A verification for the earlier brief stops proving the maker's verified waypoint, and therefore the Keeper's verified return, because it proved only that brief's work. Its private receipt receives a permanent `superseded` mark; Undo, Redo and legacy replay never clear it. The Warden keeps the check, its independence and any catch it completed, because the Warden did that check. A withdrawn verdict, unlike a superseded one, counts for nobody. A fresh verification of the revised work creates new proof for the maker. Missing eligible legacy receipts are captured before marking so later history replay cannot revive old maker proof.

Model families use a provider and model from the same recorded moment, never fields from different moments. The latest dated execution choice before a verdict takes precedence over an older hire pair. If that newer choice is incomplete, including a provider-default null model, the family is unknown and a stale independent posture earns no independent check. Legacy data without a dated choice uses a complete hire pair; if no complete pair survives, the family is unknown and the recorded review posture applies.

An already-bound quest worker records a changed pair only at an admitted turn start. The first dispatch that binds a hire token uses the hire's recorded pair. Keepers, ticks, rejected or waiting starts and unchanged pairs create no execution writes.

A failed metadata write is logged and never holds the worker's turn: that period's family and independence stay unestablished. A later successful recording or an admitted return to the cached pair ends the uncertain period; it never upgrades proof receipts already written during it.

The uncertain-period guard is in memory. If the plugin reloads while a worker whose metadata write failed is still running, later verdicts can use the stale saved pair until its next admitted start records or matches its execution. Receipts already written as unknown remain unknown.

Startup performs one idempotent backfill from existing returned and stopped quests. It uses stored maker verified wins and surviving verified entries without adding the two versions of the same credit. When several threads used one character in a quest, their old totals may overlap: the backfill takes the larger of the known distinct waypoint count and that character’s largest stored member total, never their sum. Missing waypoint identities can therefore undercount old work; the coverage boundary makes that limitation explicit. Warden counts use surviving unwithdrawn verdicts. Undone historical verdicts remain private withdrawn receipts and do not add checks or catches. Old undo history is capped and old thread journals may have been deleted, so the backfill is deliberately partial. It never reconstructs a catch from report wording or invents lost proof.

The registry read includes `serviceRecords`, an array keyed by each row's `characterId`. `firstEarnedAt` and `lastEarnedAt` describe terminal quest dates. Undated legacy rows keep their counts, sort after dated rows, and return null for `records[].endedAt` and those aggregate earned dates: show "date not recorded" rather than a substitute update or backfill date. `backfilledAt` records the backfill date. A non-null `completeSince` marks an incomplete earlier history; `warden.caughtSince` is the coverage boundary for catches. Counts include every surviving proven contribution, including earlier ones: say "recorded catches; complete since DATE", not "catches since DATE". A null boundary means the counted role's recorded history is complete. `records` is newest first and capped at twenty role contributions; `recordsTotal` and all aggregate counts cover the entire saved record.

The schema is in `src/shared/service-record.ts`. The registry RPC adds these presentation facts. The user-facing Insights view reads the same records for each character's first configured class, across all retained quests rather than the chart's selected time range. A missing class, missing record or zero earned results gives no level. Neither reader adds these facts to `runtime.snapshot`, registry preparation for agents, tools, briefs, journal text, reports, scopes or the Keeper restatement. There are no new timers or per-tick counters. Both readers aggregate stored terminal snapshots rather than rescanning event or journal history.

## Kept tales and captured levels

Keep is one presentation preference per quest and character, not per thread or role. The page changes it through `setTaleKept({ questId, characterId, kept })`; the result is `{ kept }`. Repeating the same value does not write or invalidate again. A new Keep requires a returned quest, a told tale and that character's recorded contribution. It never changes work, counts, reports, scope or agent-visible text, and it sends no message or tick.

The mutation refuses plugin callers and missing caller context. The host labels the app, CLI and agents alike as `client`, so client identity is not proof of a human. This is the accepted limitation in [host ask 2](host-asks.md#2-distinguish-human-driven-clients-from-agents), also shared by asks and Return. Tavern provides no agent tool or instruction for setting Keep.

History contains the twenty most recent role contributions plus every kept contribution, even when older. The tale list groups those rows by quest. Rows carry `told`, `available`, `kept`, the saved waypoint figures, and Warden independence counts. Only returned quests with a wrap receipt have `told: true`; stopped work never becomes a tale. Cellared quests remain available. If the quest itself is gone, counts and captured names remain, but `available` is false and its links are omitted. An orphan Keep grants nothing and can still be cleared. Legacy waypoint figures are null when no terminal snapshot was captured. New terminal snapshots also carry `waypoints.skipped`, counted separately from verified waypoints. Zero is recorded when none were skipped. Older snapshots keep that field absent, and startup backfill never infers it; absence means unknown, not zero.

New terminal writes capture each role's level before and after that quest exactly once, from prior recorded totals and the results it earned. Makers use verified waypoints, Wardens use independent checks regardless of verdict, and Keepers use returned quests with verified work. The shared `levelRole`, `earnedCount` and `levelFromCount` functions select each role's trusted count and give a level per eight results; zero results has no level. The kit, terminal snapshots and Insights use the same count and level rules, without a server import of UI code.

The tale returns flat `levels: [{ characterId, role, before, after, historyComplete }]`, or null when no credit has captured levels. Credits are projected separately, so one legacy credit never hides the others. A crossing requires `after >= 2 && after > (before ?? 1)`: the first result is silent, but a first quest earning eight results can cut a notch. With complete role history the page says “Juno reached level 2 on this quest.” With incomplete history it says “Juno was level 2 after this quest.” The latter never claims that a lower-bound count proves a first crossing. Confidence also requires no surviving membership in that role on a pre-tracking quest, even when all its credit was lost. Archived or deleted members still count; a missing linked quest cannot prove complete history. This check runs only at the terminal write. Confidence is captured with the level pair, not recomputed on read; a legacy pair with no confidence flag is incomplete. Reading or reopening a tale never recomputes the snapshot, and backfill never invents a historical crossing. Keep remains separately readable as `keptCharacterIds` even when levels are null.

Each role also has its own `firstEarnedAt` and `completeSince`, computed over all its saved contributions rather than the recent-history cap. The date is null if any contribution of that role is undated; an undated Keeper record does not erase the maker's known date. Coverage is null only when that role's contributing history is complete. A partial Keeper history does not taint the maker's level confidence.

Data backups include the typed service records, Keep flags, proof receipts and recording/backfill dates in `tavern_records`. Unlike local delivery fields, none are stripped or replayed on restore. They grant no review permission, scope, hire, allocation or delivery authority. They can contain private evidence, so the ordinary data-backup privacy warning still applies.
