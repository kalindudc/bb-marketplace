# Changelog

Notable changes to Tavern, newest first. Releases are tagged `tavern/vX.Y.Z` in this repository.

## Unreleased

### Added

- Settings lets you choose which Git program Tavern runs on its own machine. A direct Git binary used about half the CPU per Git call in a local test. Leave the setting empty to keep using Git from PATH; other machines keep their own Git.

### Changed

- Keeper acceptances stay in place when a new plan leaves the waypoint unchanged. The quest history records what carried forward.
- Tavern’s tests reuse starting Git repositories while keeping each test’s checkout and assertions independent. Transport tests prepare only the endpoints they use, and tests without a browser no longer load the browser test library.
- Journal updates in unrelated agent threads no longer trigger three Tavern refreshes. The badge loads just its count, the deleted-quests count refreshes only when it can change, and the common room reuses database reads across views.
- In light mode, faint pixel sunrays stay fixed at the strip’s upper-left corner, a warm patch follows the character’s feet, and a small highlight shimmers on the character’s outline. Their short shadow stretches as they walk and draws away as they hop. The daylight stays steady with Motion Off or reduced motion. Daytime tools and nighttime lights are unchanged.

### Fixed

- A member accepting a brief no longer wakes the Keeper on its own. The next update includes the acceptance, and members with a pending wake-up or an active keep no longer trigger stale alerts.
- Released Wardens free their checker slots. A newly hired Warden can check its assigned waypoint without the Keeper reordering the slots or making a new plan.
- Releasing a party member now archives its thread after preserving its work. Ask your Keeper to archive members released before this version.
- Keepers must reuse a resting party member before hiring if it can take the same work. The next check-in flags resting members when the quest work is done or their rest has gone stale.
- Walking sprites mirror to face their direction of travel, without changing the characters’ original faces.
- The Ledger remembers whether you fold Guardrails and opens it by default when there’s a current alert. Earlier violations stay in a separate fold, with the rule, reason and time easy to tell apart.

## 0.2.0 (2026-11-23)

Machine rules place party members on the machines you choose for each project. Keepers can lead linked quests and hand over to a fresh thread without losing open requests. The common room gathers decisions that need you, and you can reopen a returned or stopped quest when work changes. Wardens recognise the check runners your repository uses. Keepers and party members can save and find durable project notes. Animated pixel-art characters react to work and carry their own lights at night.

### Added

- At night each class carries its own light, from the Keeper’s runewood staff to the Warden’s crystal. By day they carry everyday tools instead, with a soft shadow at their feet and no cast light.
- You and the quest’s Keeper can rename an unarchived quest without changing its plan or losing its history. Choose Rename quest on the quest page to edit its title and short name. The quest history records both names and who changed them.
- Tavern classes can save and find durable project notes, and Keepers review, exclude or replace notes after they are saved. Find and manage notes on the Memory page. Built-in memory needs no setup; choose a command profile in Settings to use another store.
- Tell selected Keepers in the common room sends one unchanged message to each selected thread and shows a receipt for each. Their normal routing still applies.
- The Ledger and each quest's party show when a member's brief predates one of your steers. The Keeper receives the hint when it changes, and a delivered re-brief clears it. The path count also shows waypoints added or removed since the last greenlight.
- Agents get clearer guidance on when to keep a journal. If an agent does substantial work without starting one, Tavern can give it a private hint without opening a new turn or notifying you. Agents can add a single journal entry or start several entries for the same delegate in one call.
- In Settings, Your attention, you can send a test alert and say whether it arrived. Tavern records what happened to each alert, shows the last test and real delivery failure, and lets you close as usual if the route has not been proven.
- A carried lantern or hearth-light warms the ground and nearby edges as the character moves, without touching chat text, asks or evidence. In Settings → Atmosphere, you can turn the light off, set its strength or keep it only on Tavern's surfaces.

Work already admitted can take spend past the cap.

After restoring a backup, use Finish handover to verify a transfer before it resumes. Wake-ups from other plugins stay where they were set.

The hiring Keeper can approve a fitting child plan with Undo; if the plan needs wider limits, one card shows what changes and lets you approve the change and that plan together. You or the hiring Keeper can receive a finished child quest, but the parent waypoint still needs its own check. The original user-only asks and hand-backs stay in Needs you; the hiring Keeper sees read-only pointers. A lead confirms its own retirement once the party is released and each open pull request has an owner. Stop works from the deepest child back to the parent. Keepers and decisions lets you set the chain depth and seat ceiling. A linked quest shows its approved limits, who decides, and read-only pointers to the original child asks.
- Settings opens the bb composer with your Tavern setup request. If you have a default class, you can explicitly start the request as a plain thread. An agent reads bb’s checkouts, providers and models, then proposes a settings patch with reasons and preflight results. Review it in the thread or at the top of Settings. Its `placement` pick is a rule id from `tavern_placements` that matches the repo and class, or where the Keeper runs for its own repo only. Consent, inputs, models and forge come only from the selected rule; no Keeper-supplied target inputs are merged. A later hire with that same effective model refuses before allocation and names the class model to set in Where work runs. - A machine rule can choose a model, provider and reasoning level per class for members it places on other machines. Where work runs stages these choices behind Save rule. Hires verify the effective model and name the rule’s override in their first line; other hires keep their class settings.
- A Smith can open draft pull requests from home through a forge profile chosen by its machine rule. Where work runs lets you manage GitHub or command profiles. Tavern carries only the committed tree home, pushes the member’s own branch with a lease on later pushes, and shows the draft URL on the member card and hand-back. Existing rules keep pull requests on the member’s machine, where the Smith records a draft opened with its own tools. - Machine rules place a Keeper's newly hired working members on their own new machines. An enabled rule in Settings, Where work runs, that matches the member's repo puts every new Ranger, Smith, Warden and Wanderer hired for that repo on its own new machine, through the environment and machine providers bb's catalog offers; Tavern has no provider of its own and depends on no other plugin. Keepers stay wherever the user started them and are never moved. A lead runs where its hiring Keeper runs, unless the Keeper picks a matching enabled rule with `placement`. Only rules that ask for a new machine with a dedicated checkout run in this version; other targets save, preview, and block the hire with a plain reason.

The user's index, worktree, HEAD, refs, branches and stash are never touched; sparse checkouts are supported. The hire result's first line says where the member went, which rule placed it, and whether uncommitted changes came along and from where. A placed member is labelled "Detection only (remote)"; when its scope changes, Tavern delivers the new scope to the machine itself and shows "Scope update pending" until the machine acknowledges it.
- A Warden checks a placed Smith's work on a machine of its own. Tavern waits for the Smith to finish its turn (it never interrupts it), brings the Smith's committed and uncommitted work home under a private ref, and carries that exact tree into the Warden's checkout. A verify or reject counts only while the Warden's checkout is clean and holds the submitted tree, and the maker's journal entries, submission, waypoint and assignment are unchanged; a newer submission supersedes the review. A placed Smith with a Warden whose rule gives it no separate machine blocks the hire and names the rule to add.

A failed save keeps the thread and the machine and shows a blocker with Retry. Declared files that live outside the member's checkout and thread storage, or no longer exist, are listed as not saved with the reason. A member whose thread or machine was lost outside Tavern is released with a plain note that its work was not saved, never recorded as saved. The private snapshot refs Tavern keeps in the home checkout are described in `docs/machines-snapshots.md`.

A machine that is still starting shows its provider's name, never an invented host name. The Keeper's ledger says where its party would run when a rule could apply to its project, and `tavern_status section=placement` gives the full picture per class with the slots in use.
- A returned or stopped quest can be re-opened for deviations and follow-up commits without opening a new quest. `tavern_reopen` returns it to scouting when no plan was greenlit, or to build otherwise, keeps its plan version and greenlight, clears its end and stop state, records `quest.reopened`, and reanchors the Keeper's thread. A live quest is refused; an archived quest must be brought up from the cellar first, and a deleted one restored from there.

### Changed

- A Ranger’s check-in is a report, not a finish. The Keeper can accept the findings, continue scouting within the minutes budget, or release or replace the Ranger. The Ledger shows when the Ranger is waiting on its Keeper.
- Rangers can run local programs and pipe input into them. Checked write paths, Git changes, sends and cluster writes still have guardrails.
- Wardens can run local programs like Gradle and Java without a tool grant. Checked write paths, Git and network write rules still apply. When Tavern cannot parse a shell command, it shows the parser’s error and a command excerpt.
- Carried lights breathe at their own pace at night. The halo follows the source, and the pool on the ground widens and dims during a hop. The pixelated light fades before the strip’s edges. By day the shadow stays on the ground and softens as the character rises. Motion Off and reduced motion keep the light steady.
- The Keeper’s widget stays on one row. Open asks, new items or quest progress in place from their chips, or use the chevron to open what needs your attention first. Keeper state is short; the shield opens the full guard details in the Ledger. The Ledger and Journal still open their own panels.
- The Keeper handles blocked calls first. Scope blocks stay in the member alert, the Ledger and quest history, but no longer ask you to review them. Older review-only asks are marked moved to the Keeper. You still decide exact scope grants and can confirm a Pi restart when only you can repair a missing guard. Unreadable write targets are refused without being called outside the allowed roots.
- The README and documentation explain how to run a quest, steer its party and make decisions. The marketplace listing starts in the fictional Demo Notes Keeper thread and shows the quest map, an ask in the composer and the Journal tab.
- The shell guard applies the same protections across machine providers: rotate, park, and remove are configuration changes, and create and enroll are machine allocation, for `bb` command groups ending in `-machines`.
- Agents with an active guard cannot send messages as you, even in Watch or Off. The Keeper can hand you a blocked send only after checking that its recipient and message are known. Scopes accepts tool patterns and shell command prefixes. Named-target draft approvals wake the member for one exact call. Older guards keep their ordinary scope and need a restart for the send guard. If the message policy and scope disagree, Tavern reports it and holds recognized sends and drafts without stopping unrelated work.
- Reports label confidence percentages as the member’s own estimate, not a Warden verdict.
- New party members take their names from their own Keeper’s party, so two Keepers can each hire a Juno. A resting member keeps its name, and existing numerals stay unless there is a conflict. The mention list puts your party first. It, the common room history and the map name the Keeper where parties meet. The member widget shows the current waypoint and, when different, the one named by the latest report.
- Every new Keeper promise has a deadline. When the promise comes due, Tavern tells the Keeper what it was waiting for. A member that reports a wait gets no stale strikes before its deadline, and a blocked report with a declared wait does not send you an alert. The Keeper sees fresh gate warnings and the first two stale strikes, not the same reminder every tick. A member whose thread is still busy but has no recent progress evidence prompts one quiet hint to the Keeper. Older promises without a deadline stay in the ledger and say so.
- Member reports and cleanup no longer make the rest of bb wait for Git. A report makes four fewer Git calls, and cleanup makes eight to twelve fewer on the tested checkouts. Rebase checks also run without blocking bb.
- The journal and read-as line no longer make the browser recalculate layout when you open a thread panel or update something unrelated. They still remember their widths when they resize.
- Tavern’s background check runs every five seconds and now does about 80% less database work. It checks each Keeper’s thread once instead of twice when no brief needs retrying, and skips writes when the saved state hasn’t changed.
- Tavern reuses unchanged Git configuration and checkout facts. In tests, preparing a member call needed 2 Git launches instead of 12, and capturing a checkout with uncommitted work needed 28 instead of 64.
- Where the shell guard is armed, cluster writes need approval and a separate confirmation on the same card. The confirmation allows one run by the named thread and expires if unused. The Keeper row says when cluster writes are not prevented and stays quiet when the guard is armed. Ordinary reads on a placed member’s machine are inspected without waiting for a command receipt.
- Characters walk with their own stride and pace. Their shoulders bob less, their heads follow a beat later, and their tools and lantern sway more gently. They glance around as they walk and occasionally while standing, without changing the idle's breathing or tool beats. Calm stays in place and uses smaller hops. Characters still react to clicks beside an ask without moving the ask or its marker. With reduced motion, Motion Off or Quiet, a click turns the character in place.
- The member history records when a member joined, took a brief, finished work, was released, stopped, or archived. A stopped member is no longer labelled released, and a returned quest does not list its finished members as resting. Failed members keep their slot until the Keeper releases them or retries their work. Failed errands appear with recent errands and say when they still hold a slot. Rest reminders still leave release to the Keeper. On a separate machine, Tavern confirms that work was saved or that its loss was reconciled before it frees the allocation.
- Cluster writes always ask you, even when you have delegated other production decisions. A scope cannot grant them. A confirmed cluster command and an ordinary shell grant can wait in the same member without interfering. The ask shows the exact command, any contexts and namespaces it names, and what would change. Consequential asks also show undo instructions when the Keeper provides them. A Kubernetes port-forward is not treated as a read, and read-only host scopes still do not run `terraform plan`.
- Every Tavern settings row shows its default and lets you reset it. Keeper pacing and memory knobs show who last changed them, and live quest overrides can be ended from Settings. Always ask routes the kinds you choose, without weakening verdict requirements. Closing time saves the guard selection with each window; the default keeps the previous protections.
- Atmosphere in Settings brings character visibility, speech bubbles, levels and ambient motion together, and links to the character sheets for rolling avatars. It keeps the existing settings and explains when speech also affects replies and reports.
- A rule that places a Keeper must name keeper in its classes, or name no classes.
- Machine placement carries files with porcelain Git on members' and Wardens' machines without requiring member-side object or index plumbing. Changed-path queries and bounded tree/index listings provide full object IDs even when Git abbreviates raw diffs. Successful commands may emit configuration warnings; their exit code determines success. Carries start only at the recorded commit with no foreign work, keep write-ahead marks for interruptions, and commit only the declared paths with Tavern's identity and the message `Tavern carried snapshot`, never impersonating the maker. Tavern never resets a member's branch. A changed HEAD blocks the carry and asks for preservation and reconciliation. Home computes each delta from the previous carried tree and verifies the rebuilt snapshot before a review or draft pull request can use it. Large-repository steps share a five-minute budget; quick Git reads retain their shorter limit.
- The recorded Agents may change settings grant still permits non-guardrail CLI changes when enabled. Managed threads cannot change guardrails, and the Settings-page RPCs remain user-only. Built-in classes follow the user’s party ceiling. Custom classes retain their smaller soft size, exceeded only by a one-use recorded decision and never past that ceiling. Review allowances are offered only at the budget and unused grants end with the quest. User receipts are passed explicitly into their own transactions, never inherited by background ticks, delivery or overdue promises.
- User-only controls share one authority policy. Plugin calls and client calls marked as an agent, thread or CLI are refused, including rule changes, Stop, Undo and route corrections. Unmarked clients remain unattributed: answer receipts say “answered from a client Tavern could not attribute”. The terminal refuses user-only commands from a thread.
- Asks carry their exact transition effect. An answer and its saved state changes commit together; delivery, scope installation and thread cleanup follow through their existing recovery paths. Old asks acquire a typed effect when read, and every withdrawal records its cause once. Class party size and Ranger capacity remain soft limits: a recorded reversible Keeper decision can exceed either once, but never the hard party ceiling or review budget.
