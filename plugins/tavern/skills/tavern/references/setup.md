# Guided setup reference

Use this workflow when the user asks you to discover their environment and propose Tavern settings.

1. Run `bb tavern setup discover` to read bb's current facts as JSON. It lists registered checkouts and known default branches, normalized project remotes, offered environment and machine providers, model catalogs, and the current Tavern settings revision and placement policy. Narrow with `--project <id>` or `--host <id>`. An unknown branch or catalog error is not evidence of a default or of model availability.
2. Check what the SDK does not know on the intended source host. Run `git remote -v` to inspect actual fetch and push remotes, `command -v` for the forge CLI, and `gh auth status` when using `gh`. Inspect script paths on disk without running unreviewed scripts. Keep project-specific preferences in the user's configuration, never in the base skill.
3. Run `bb tavern setup propose --toml "<PATCH>" --reasons '<JSON>'` once you know what to change. Put only the changed settings in TOML. Key `reasons` by camelCase dotted path, such as `{"classes.smith.model":"Use the model you picked."}`, with one line per changed key. Because `machines.rules` and `machines.forges` are ordered arrays, copy unchanged rows into the array from `bb tavern settings export` (TOML) or `placement` in discovery (camelCase JSON, converted to snake_case TOML). See [setup examples](settings.md#setup-examples). Do not use a full settings import, which resets omitted explicit values and pins.
4. For new or changed command forge profiles, pass single absolute executable paths without arguments for `open`, `state`, and `close`. Paths must sit outside agent checkouts and thread storage, including symlinks resolving there. Every script must support a read-only `--help` flag that exits 0 without side effects. Tavern checks paths and catalogs before showing the proposal and runs `--help` only when the user clicks Apply. Models for unprovisioned machines are marked not checked yet and verified when the first member starts there.
5. Emit the returned `::tavern-setup{id="…"}` directive on its own line. Every setup proposal waits for the user's Apply regardless of its keys; the user can review or dismiss it from the thread or Settings. Never apply a proposal for the user. If a targeted setting changed or a preflight check fails, fix the issue and propose again.
6. Ask the user to open Tavern Settings, Your attention, and press "Send a test alert". Have them check their device and choose "It arrived" or "It did not". Only the user should send and answer the test, and a successful send alone does not prove device delivery.
